# Ravenclaw University audit — 2026-11-18

Audited revision: `717f475`. This is a diagnostic report; application behavior and
dependencies were not changed. All registration, password, upload, content-delete
and concurrency tests used a GUID-named disposable SQL database and separate upload
storage. The actual university database received no writes. The normal app remains
at localhost:5182.

## Result

Core authentication, authorization and CRUD flows passed. Eight code/dependency
findings remain: **one P1, six P2, one P3**, plus the separately tracked recurring
local SQL connection-stability risk. No P0 release-blocking functional failure was
observed in the tested flows. The application is not cleared for production solely
on this result: its target framework is now unsupported, and deployment/HTTPS and
physical-device coverage remain incomplete.

Implementation-integrity verdict: the interface has a coherent Ravenclaw-specific
navy/ivory/gold system, consistent account/admin shells and a shared ADMIN badge.
The source detector found no findings in this run. Functional edge cases below
still need repair.

## Findings

### F1 — P1: Target framework is out of support

Location: `241611JalopFinalQuiz2/241611JalopFinalQuiz2.csproj:4`.

The project targets `net9.0` and references EF Core `9.*`. Microsoft ended .NET 9
support on **November 10, 2026**, before this audit date. A successful local build
does not establish continued runtime security support.

Recommendation: plan and verify a move to a supported target framework and matching
EF Core major version, preserving the database-first model and consolidated schema.
Treat this as a separate upgrade with a full regression and publish check.

Source: [Microsoft .NET 8/9 end-of-support notice](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/).

### F2 — P2: Mobile About dots stop on an intermediate chapter with long content

Location: `241611JalopFinalQuiz2/wwwroot/js/about-story.js:39`, particularly lines
47–58 (`sizeRail`, height-collapse scroll correction, smooth scrolling).

Reproduction: at 390×844, make the introduction substantially taller than Mission
(the audit used 80 short lines of browser-injected text, a state allowed by the
editable description field). From Introduction, click Vision or Core Values.
Both tests finished on **Mission**, selected index 1 / scrollLeft 414px, instead of
the requested index 2 or 3. With the short baseline fixture all four dots worked;
reduced-motion instant selection also worked.

Impact: navigation is unreliable for valid long university copy. The chapter-height
correction invokes `scrollIntoView` while horizontal smooth scrolling is in progress.

Recommendation: preserve the requested target through the transition, settle the
horizontal movement before vertical correction, and size the rail without cancelling
the active scroll. Retest long-to-short and short-to-long jumps, reduced motion,
resize and touch. Suggested UI follow-up: `impeccable animate`.

### F3 — P2: Cancel after server validation preserves the rejected values

Location: `241611JalopFinalQuiz2/wwwroot/js/profile-editor.js:53–65` and
`241611JalopFinalQuiz2/Controllers/ProfileController.cs` personal-details invalid POST.

Reproduction: enter Birthday `2999-01-01`, submit, then click Cancel after the server
rejects it. Birthday remains **2999-01-01**, while the validation message disappears.
The server-returned invalid values have become the native reset baseline, and reset
also clears the recovered-draft flag.

Impact: Cancel can appear to discard edits even though the rejected value remains;
the page then treats it as clean. No invalid birthday was saved in the database.

Recommendation: Cancel should restore persisted values or reload the saved Profile
state. Do not clear validation/draft state while keeping unsaved invalid values.
Suggested follow-up: `impeccable harden`.

### F4 — P2: Signature-only image validation accepts an invalid image

Location: `241611JalopFinalQuiz2/Services/ImageUploadService.cs:20–29`.

Reproduction: upload a `.png` consisting of the 8-byte PNG signature followed by
four zero bytes, for a total of **12 bytes**, through About Gallery. The server
returned **302 success**, wrote the upload, and the saved image rendered broken
(`naturalWidth` 0). The service is shared by hero, programs, gallery and profiles.

Impact: corrupted uploads can be persisted and published. This test did not show
script execution: extension restrictions, server-managed paths and upload `nosniff`
are separate protections and remain in place.

Recommendation: validate that supported images can actually be decoded, with
bounded dimensions/pixel count and resource usage. Continue checking signatures,
extensions and byte limits, and discard failed uploads. Add corrupt/truncated JPEG,
PNG and WebP cases. Suggested follow-up: `impeccable harden`.

### F5 — P2: Automatic program scrolling loses fractional movement

Location: `241611JalopFinalQuiz2/wwwroot/js/program-showcase.js:55`.

The animation adds `delta * .025` directly to the current `scrollLeft` each frame.
In a 1440×900 Chromium run with the rail fully visible, no hover/focus/open cards,
reduced motion off, and the document visible, **119 frame intervals over 2133ms**
advanced the rail only **1px**. The average interval was 17.93ms. An explicit `+0.4`
write did not change scrollLeft; a `+1` write did. The intended speed for 2133ms is
about 53px, so per-frame rounding discards most movement.

Impact: the automatic carousel can appear stopped at ordinary refresh rates.
Manual scrolling and keyboard disclosure still worked.

Recommendation: accumulate a floating-point target position independently of the
browser's rounded scroll position; reconcile it with drag/manual scroll and wrapping.
Test 60Hz and higher refresh rates. The first history test suggested a Back-button
issue, but the focused run did **not** restore from bfcache; no separate bfcache
failure is claimed. Suggested follow-up: `impeccable animate`.

### F6 — P2: Concurrent duplicate registration produces a generic server failure

Location: `241611JalopFinalQuiz2/Services/AccountService.cs` serializable creation
transaction and `Controllers/AccountController.cs` registration exception handling.

Reproduction: submit two simultaneous valid registrations for the same username.
One returned 302 success; the other returned 200 with Registration is temporarily
unavailable. SQL logged **1205 deadlock victim**. A read-back found exactly one
matching account, so uniqueness protection worked.

Impact: normal concurrent usage can fail with an operational error instead of the
expected username-in-use message. This is not a demonstrated duplicate-account or
authorization vulnerability.

Recommendation: bounded handling of SQL deadlock retries followed by a fresh
duplicate check; keep first-admin and username protections transactional. Do not
change the agreed schema implicitly. Suggested follow-up: implementation hardening.

### F7 — P2: Build dependencies have an active high-severity advisory

Location: root `package-lock.json`; resolved chain:
`@tailwindcss/cli@4.3.5 → @parcel/watcher@2.6.0 → picomatch@4.0.7`.

`npm audit` reported three high-severity affected entries from one underlying
picomatch repeated-extglob ReDoS advisory. The advisory covers versions through
4.0.7 and listed **no patched version** when checked. These packages are development
build/watch dependencies, not the ASP.NET application runtime. The audit did not
establish that a website user can feed patterns into this toolchain.

Recommendation: keep build/watch inputs trusted, track a compatible corrected
dependency release, and review the dependency tree before changing versions. Do not
blindly run `npm audit fix --force`; the feed suggested a CLI downgrade, which needs
compatibility assessment.

Source: [GitHub advisory GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf).

### F8 — P3: Privacy route still contains starter placeholder copy

Location: `241611JalopFinalQuiz2/Views/Home/Privacy.cshtml:6`.

An authenticated GET to `/Home/Privacy` returns the starter sentence asking the
developer to detail the site's privacy policy. It is a reachable unfinished page,
even though it is not part of the main navigation.

Recommendation: decide whether this route belongs in the submitted site. Remove
the unused route/view or replace it with approved factual copy. No policy text was
invented during this audit.

## Operational finding: recurring SQL connection instability

Earlier user sign-ins and the initial audit browser run encountered SQL connection
timeouts; the disposable server log also contains SqlClient error -2. Some first-pass
browser navigation waits timed out. The final DOM-readiness matrix succeeded on
all 52 checks, so these were not classified as deterministic route failures.

At the end of the audit, SQL's `process_physical_memory_low` flag was **0**, the
actual site's login GET returned 200, and a CSRF-protected POST with a nonexistent
diagnostic username reached normal credential rejection in **61ms**. This is a
current successful sample, not proof that the intermittent problem is resolved.
Prior low-memory observations remain relevant but do not prove the sole cause.

Recommendation: capture timed SQL/OS telemetry during the next failure, including
memory, scheduling/I/O and login waits. Avoid hiding the issue with relaxed
encryption or simply increasing timeouts. No SQL configuration was changed.

## Additional observations and limits

- A wrong-current-password error renders safely with empty password inputs, but
  the manual password input has neither `aria-invalid` nor `aria-describedby` linking
  its error. axe reported no violation in that error state. Improve the programmatic
  association and focus handling when hardening forms; this is not counted as a
  separate confirmed WCAG failure.
- SQL serializable safeguards protected the last/current admin and duplicate
  usernames. CSRF, role tampering, stored-text encoding, upload size/type checks,
  old-password rejection and password-hash preservation were exercised successfully.
- No source/dependency repair was made during this diagnostic audit. Confirmed
  unfinished implementation is listed in STATUS.md.
- Hidden gallery/Collegiate Circle interactions were not treated as public-page
  features; the retained gallery editor itself was tested.
- Runtime tests used installed desktop Chrome/Chromium and a local Development
  environment. Physical iOS/Android, Safari/Firefox, assistive-technology sessions,
  production HTTPS/reverse proxy, load testing and long-duration session expiry
  were not verified. Password changes still revoke only the current session, as
  documented; session-wide revocation is outside the existing scope.
- First-admin interactive terminal provisioning was reviewed in source, but no
  real admin was created or reset. The build/publish and dependency scans do not
  substitute for deployed-environment verification.
- Screenshots show disposable fixture content, not the user's published records.
  Local raw evidence is retained under ignored `TestResults/FullAudit/`.

Suggested repair order: supported-framework plan, form/upload/concurrency hardening,
About/carousel animation fixes, development-dependency mitigation, then the unused
Privacy route. For UI work, use `impeccable harden`, `impeccable animate`, and finish
with `impeccable polish`; these can be applied individually or together. Re-run the
regressions and audit after repairs rather than treating this score as permanent.
